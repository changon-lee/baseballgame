# 야구 규칙·주루·수비 문제와 개선 방안

작성·갱신일: 2026-11-05  
상태: 코드 분석 및 개선 제안. 이 문서 작성으로 게임 코드를 변경하지 않았다.

## 1. 목적과 분석 기준

현재 워크스페이스에서 확인한 문제를 규칙 오류, 화면과 판정의 불일치, 현실성 부족, 기능 미구현으로 구분한다. 각 문제의 원인과 재현 사례, 해결 방향, 구현 순서 및 검증 기준을 정리한다. 아래 작업 단계는 권장안이며, 구현 완료나 범위 확정을 뜻하지 않는다.

한 경기는 삼성 홈으로 고정된다. 사용자는 초에 투구하고 말에 타격한다. `js/core/`가 공 하나의 결과와 다음 경기 상태를 계산하고, `js/ui/art/playscript.js`가 결정된 결과에 맞는 움직임을 생성한다. `js/ui/game.js`는 장면 재생 후 계산된 상태를 반영한다. 화면에서 실제 포구 여부를 판정해 안타와 아웃을 정하는 구조가 아니다.

이 구조는 유지하되, 점수 계산과 주자 이동, 송구·포구·태그가 하나의 결과 데이터를 공유하도록 개선한다. 완전한 물리 시뮬레이션으로 재작성할 필요는 없다.

분석 과정에서 기존 자동 테스트 126개가 통과했다. 이는 현재 구현에 대한 회귀 검사 결과이며, 야구 규칙과 모든 장면의 정확성을 보장하지는 않는다. 아래 재현은 코어 함수와 애니메이션 시간표 계산 기준이다. 브라우저 화면을 직접 조작해 관찰한 결과와는 구분한다.

## 3. 문제 상황과 해결 방안

### R1. 끝내기 안타의 초과 득점

**재현:** 9회말 0:0, 2·3루에서 `SINGLE`을 적용하면 홈팀 점수가 2점이 되어 2:0으로 끝난다. 정상적으로는 3루 주자의 결승점으로 1:0 종료다. 장외 홈런은 전원 득점을 인정하는 예외다. 근거는 공식 야구규칙 7.01(g)(3)과 9.06(f)다. [자료 1](#8-규칙-확인-자료)

**원인:** `rules.js`가 타구 이벤트의 득점을 모두 더한 후 끝내기를 검사한다. `match.js`의 타석 기록과 `growth.js`의 타점·실점 집계에도 같은 값이 전달된다.

**해결:** 일반 안타의 끝내기는 승리에 필요한 득점까지만 인정한다. 장외 홈런의 전원 득점 처리는 유지한다. 장기적으로는 득점 순서를 포함한 공통 주루 데이터에서 결승점 이후의 동작과 기록을 종료한다. 끝내기 상황의 안타 종류도 결승 주자의 진루와 타자주자의 실제 도달 베이스에 맞춰 기록해야 한다.

**검증:** 동점·1점 차·2점 차에서 여러 주자가 있는 끝내기 안타, 밀어내기 볼넷, 장외 홈런을 각각 검사한다. 스코어보드, 타석 로그, 타점, 투수 실점이 같은 인정 득점을 사용해야 한다.

관련: [`rules.js`](../js/core/rules.js), [`match.js`](../js/core/match.js), [`growth.js`](../js/core/growth.js)

### V1. 희생플라이 송구와 포구의 시간 불일치

**재현 조건:** `buildPlay({ event: 'SAC_FLY', fly: true, bats: 'R', contact: { pull: 0 }, bases: [false, false, true], rng: createRng(seed) })`. 매 장면마다 시드 1~300으로 RNG를 새로 생성했다.

이 조건의 300개 장면 중 196개에서 송구가 주자보다 먼저 홈에 도착했다. 시드 2의 시간표는 다음과 같다. 시간 단위는 대본 내부의 초이며, 화면에서는 `SPEED = 1.3` 배속으로 재생된다.

| 동작 | 타격 후 시각 |
|---|---:|
| 송구 구간 종료 | 7.583초 |
| 3루 주자 홈 도착 | 7.695초 |
| 포수가 공을 보유하는 구간 시작 | 7.995초 |

**원인:** `throwBall()`로 송구 도착을 계산한 뒤 `receive()`에는 `Math.max(arr, home + 0.3)`을 전달한다. 두 시각 사이에는 공이 송구 종점에 머무르는 구간이 생긴다.

**해결:** 송구 도착과 포구를 같은 시각으로 처리한다. 포구 후 태그가 필요한 플레이는 태그 동작과 시각을 별도로 둔다. 세이프 장면은 주자가 태그보다 먼저 들어오거나, 수비수가 태그를 놓치는 등의 일관된 동작으로 표현한다. 공이 먼저 도착했다는 이유만으로 자동 아웃 처리해서는 안 된다.

**검증:** 송구 종점 시각과 포구 시각이 일치하고, 태그 아웃은 포구 뒤 실제 태그 시점에 발생해야 한다. 위 재현 수치는 특정 입력의 결과이며 전체 경기 발생률을 뜻하지 않는다.

관련: [`playscript.js`](../js/ui/art/playscript.js)의 `throwBall()`, `receive()`, 희생플라이 분기

### V2. 땅볼·병살 때 주자가 리드 위치에 정지

**재현:** 만루에서 `DOUBLE_PLAY` 장면을 생성하면 타자와 1루 주자만 움직인다. 2·3루 주자는 초기 리드 좌표에 그대로 있고 동작만 `stand`로 바뀐다. 일반 땅볼 아웃도 나머지 주자의 진루·귀루가 빠져 있다.

**사용자 관찰 사례 — 1루 주자가 있는 병살성 땅볼:** 기존 1루 주자가 2루로 뛰지 않고, 타자주자만 1루로 달리다가 아웃된다. 화면에서 관찰된 이 현상은 일반 땅볼 `OUT` 분기의 이동 누락과 일치한다. 해당 장면의 실제 이벤트 로그를 확보한 것은 아니므로, 화면만 보고 `DOUBLE_PLAY` 판정 자체가 실패했다고 단정하지 않는다.

현재 코드에서 `DOUBLE_PLAY`로 선택되면 기존 1루 주자에게 2루 이동 경로를 만들고 2루 → 1루 송구를 연결한다. 반면 일반 땅볼 `OUT`이면 타자주자에게만 이동 경로를 만들고, 기존 1루 주자는 초기 리드 위치에 세운 채 경기 상태에서도 1루에 남긴다. 따라서 병살성으로 보이는 타구라도 일반 아웃으로 선택되면 사용자 관찰과 같은 장면이 가능하다.

**원인:** 땅볼 분기가 주로 타자주자와 병살 대상인 1루 주자만 처리한다. 마지막 보정은 이동 경로가 없는 주자를 현재 위치에 세울 뿐이다. 규칙 엔진도 `OUT`은 아웃 하나만 증가시키고, `DOUBLE_PLAY`는 1루 주자만 제거한다.

**해결:** 먼저 아웃 순서와 주자별 최종 상태를 정하고 모든 주자에게 진루·귀루·아웃 중 하나의 경로를 부여한다. 1단계에서는 현재 최종 베이스 상태를 유지하면서 귀루 누락을 막고, 2단계에서 상황별 진루를 추가한다. 주자는 다음 공 준비 전까지 합법적인 최종 위치에 있어야 한다.

1루 주자가 있는 병살성 땅볼은 다음 수비 결과를 구분한다. 병살성 타구가 반드시 병살이 되어야 하는 것은 아니다.

| 수비 처리 | 기대하는 주루·판정 |
|---|---|
| 2루에서 선행 주자 아웃 → 1루 송구도 성공 | 기존 1루 주자가 2루로 뛰고, 타자주자와 함께 아웃. 병살 가능한 아웃 수에서만 적용 |
| 2루에서 선행 주자만 아웃 | 기존 1루 주자는 2루에서 아웃, 타자주자는 1루 생존. 야수선택으로 기록 |
| 타자주자만 1루에서 아웃 | 기존 1루 주자는 타구와 아웃 순서에 맞춰 2루로 진루하거나 포스 해제 후 1루로 귀루. 리드 위치에 정지시키지 않음 |

**추가 검증:** 1루만 점유한 0·1아웃 상황에서 위 세 결과를 각각 검사한다. 기존 주자와 타자주자를 구분해 이동 경로, 아웃 대상, 최종 베이스, 증가한 아웃 수, 경기 기록이 모두 일치해야 한다. 2아웃에서는 세 번째 아웃으로 플레이를 끝내며 병살 동작을 강제하지 않는다. 일반 `OUT`으로 처리하더라도 기존 주자의 이동 누락이 다시 발생해서는 안 된다.

**규칙상 주의:** 땅볼이라는 이유만으로 모든 주자를 한 베이스씩 밀어서는 안 된다. 타자주자가 먼저 아웃되면 포스가 해제될 수 있다. 무사 만루 병살에서도 득점과 진루는 아웃 순서·송구 선택·주자의 실제 이동에 달려 있다. 반대로 1사에서 세 번째 아웃이 포스 아웃이거나 타자주자의 1루 도달 전 아웃이면 득점은 인정되지 않는다. [자료 1, 2](#8-규칙-확인-자료)

관련: [`rules.js`](../js/core/rules.js), [`playscript.js`](../js/ui/art/playscript.js)

### R2. 뜬공 아웃을 희생플라이로 자동 전환

**현재:** `outcome.js`는 뜬공 아웃이고 3루 주자가 있으며 2아웃 미만이면 무조건 `SAC_FLY`를 반환한다. 이후 대본은 깊은 외야 플라이와 득점을 보장하는 장면을 만든다.

**해결:** 타구의 깊이·방향과 포구 위치를 먼저 정한 뒤 태그업 시도와 성공 여부를 결정한다. 얕은 플라이에서는 주자가 잔류할 수 있고, 홈 승부에서는 아웃도 가능해야 한다. 희생플라이는 실제 인정 득점이 성립한 경우의 기록으로 산출한다. 1·2루 주자의 태그업도 주자 이동 데이터로 표현한다. [자료 3](#8-규칙-확인-자료)

초기에는 타구를 얕음·보통·깊음으로 구분하는 정도로 시작할 수 있다. 깊이 기준과 시도 확률은 조정 가능한 설정으로 두되, 구체적인 수치는 밸런스 검증 후 정한다.

관련: [`outcome.js`](../js/core/outcome.js), [`playscript.js`](../js/ui/art/playscript.js), [`growth.js`](../js/core/growth.js)

### R3. 안타별 진루 고정

| 이벤트 | 현재 동작 | 개선 방향 |
|---|---|---|
| 단타 | 2·3루 주자 항상 득점, 1루 주자는 2루 | 짧은 안타와 깊은 안타를 구분해 2루 주자의 홈 진입, 1루 주자의 3루 진루 결정 |
| 2루타 | 2·3루 주자 득점, 1루 주자는 항상 3루 | 깊이·방향·출발 시점에 따라 홈 또는 3루 |
| 3루타 | 모든 기존 주자 득점 | 기본 처리를 유지하고 경로·도착 순서 검증 |

현재의 각 진루가 개별적으로 규칙 위반인 것은 아니다. 모든 타구에서 같은 결과가 나오는 것이 현실성 문제다.

**해결:** 타구 종류·깊이·방향·아웃 수로 주루를 결정한다. 초기에는 공통 주루 속도로 시작하고, 선수별 주력은 후속 확장으로 둔다. `fly`는 뜬공 여부일 뿐 깊이나 수비 난도를 나타내지 않으므로 이것만으로 진루를 고정하지 않는다. 땅볼도 외야 깊숙이 빠질 수 있다.

관련: [`rules.js`](../js/core/rules.js)의 안타 분기, [`playscript.js`](../js/ui/art/playscript.js)의 `dest`

### V3. 결과를 맞추기 위한 속도 조절과 반복 동작

**확인한 구현:**

- 땅볼 아웃의 타자는 송구보다 최소 0.22초 늦게 1루에 도착하도록 시간을 늘린다.
- 뜬공 포구에서는 수비수가 시간 내 도착하도록 이동 속도를 높일 수 있다.
- 땅볼 안타의 내야수는 공까지 거리의 72%만 이동해 다이빙한다.
- 2·3루타는 마지막 송구가 주자보다 늦게 도착하도록 중계 릴리스를 미루기도 한다.
- 아웃 타구는 수비수 위치 쪽으로 방향을 다시 정하고, 땅볼 안타는 네 개의 기본 방향 중 하나를 다시 뽑는다. 스윙 방향과 장면 방향의 연결이 약해진다.

**해결:** 주루·수비·송구 속도를 합리적인 범위로 제한한다. 선택된 결과가 성립하도록 타구의 위치·속도·수비 동선을 조정한다. 제한된 횟수 안에 장면을 만들고, 실패하면 검증된 기본 장면으로 대체한다. 무한 재생성이나 선수 속도의 무제한 증가는 피한다. 당겨침·밀어침의 방향도 가능한 범위에서 보존한다.

**검증:** 이동 속도 상한, 불필요한 공 보유 대기, 송구·포구 연결을 검사한다. 반복 다이빙과 급격한 이동은 브라우저에서도 시각적으로 확인한다.

관련: [`playscript.js`](../js/ui/art/playscript.js)의 `catchFly()`, `batterTo1B()`, 안타 분기

### V4. 2아웃에서도 플라이 포구를 기다리는 주자

**원인:** `buildPlay()`에 현재 아웃 수가 전달되지 않는다. 일반 플라이 아웃은 주자가 몇 걸음 나갔다가 포구 후 돌아오는 경로를 만든다.

**해결:** 공통 경기 결과에 타격 전 아웃 수를 포함한다. 2아웃이면 타격 직후 주자가 출발하고, 잡혀 세 번째 아웃이 되면 플레이를 종료한다. 2아웃 미만에서는 포구 확인과 태그업·귀루를 구분한다.

관련: [`game.js`](../js/ui/game.js)의 `buildPlay()` 호출, [`playscript.js`](../js/ui/art/playscript.js)

### D1. 수비 선택 부족

**현재:** 일반 땅볼은 타자주자의 1루 아웃, 병살은 2루 후 1루 처리에 집중되어 있다. 선행 주자만 아웃시키고 타자가 사는 야수선택, 홈 포스 플레이, 태그업 홈 아웃이 없다. 투수·포수는 타구를 처음 처리하는 후보에 포함되지 않는다. 포수의 송구 수신이나 투수의 플라이 이후 중계 수신은 있으므로, 이들이 공을 전혀 받지 않는다는 뜻은 아니다.

**해결:** 공통 주루·아웃 데이터가 준비된 후 야수선택, 홈 승부, 투수·포수의 타구 처리를 순서대로 추가한다. 아웃 대상·베이스·포스/태그 구분을 명시한다. 새 결과는 화면 문구뿐 아니라 타수·안타·타점·투수 기록과 자동 경기에도 반영한다. 야수선택 출루를 안타로 집계해서는 안 된다.

병살 확률 35%는 현재 설정값이다. 비교 가능한 실제 통계 없이 과도하다고 단정하거나 15%로 고정하지 않는다. 타구·수비 선택을 개선한 후 실제 시뮬레이션 분포를 보고 조정한다.

관련: [`outcome.js`](../js/core/outcome.js), [`rules.js`](../js/core/rules.js), [`match.js`](../js/core/match.js), [`growth.js`](../js/core/growth.js), [`playscript.js`](../js/ui/art/playscript.js)

### S1·S2. 시즌 운영 규정과 게임 설정의 차이

2026 KBO 공식 안내에 따르면 와일드카드는 최대 2경기이고 4위는 1승 또는 1무로 진출하며 5위는 2승이 필요하다. 포스트시즌 연장은 최대 15회이고 한국시리즈 홈 편성은 2-3-2다. [자료 4](#8-규칙-확인-자료)

현재 와일드카드는 4위에 1승을 부여한 2선승제지만 무승부는 모든 시리즈에서 승수 없이 재경기한다. 4위의 무승부 진출을 별도 처리해야 한다. 준플레이오프 이후 무승부 경기의 재편성도 실제 운영과 같지 않다.

삼성은 정규·포스트시즌 모두 홈이고, 연장은 설정 이닝 +2회다. 와일드카드 무승부는 독립적인 규칙 수정으로 처리하고, 홈/원정 전환과 실제 연장 제한은 후속 작업으로 분리한다. 단축 경기 설정을 유지할 경우 실제 KBO 규정과 게임용 설정을 화면에서 구별할 수 있어야 한다.

관련: [`season.js`](../js/core/season.js), [`rules.js`](../js/core/rules.js), [`config.js`](../js/config.js), [`main.js`](../js/main.js)

## 4. 권장 설계: 판정과 화면이 같은 데이터를 사용

현재 `rules.js`와 `playscript.js`는 주자의 최종 도착 베이스를 별도로 결정한다. 하나만 수정하면 점수와 화면이 어긋나기 쉽다. 타구 결과를 만드는 단계에서 주자 이동과 아웃을 함께 결정하고, 상태 갱신과 화면 재생은 이를 소비하도록 한다.

```text
투구·스윙 판정
  → 타구 특성 및 수비 선택
  → 주자별 이동·아웃 순서·인정 득점 결정
  → 같은 결과로 경기 상태와 타석 기록 계산
  → 같은 결과를 만족하는 움직임 생성·검증
  → 화면 재생 후 준비된 경기 상태 반영
```

다음은 데이터 형태의 예시이며 실제 API 확정안은 아니다. `from: 0`은 타자, `to: 4`는 홈을 뜻한다.

```js
{
  event: 'SINGLE',
  outsBefore: 1,
  battedBall: { kind: 'ground', depth: 'deep', direction: 'right' },
  advances: [
    { from: 0, to: 1 },
    { from: 1, to: 3 },
    { from: 2, to: 4 }
  ],
  outs: [],
  runs: 1
}
```

홈 승부와 세 번째 아웃까지 다루려면 다음 정보도 필요하다.

- 이동·득점·아웃의 순서와 대상 주자.
- 아웃 종류: 포스, 태그, 뜬공 포구, 타자주자의 1루 도달 전 아웃 등.
- 득점 인정 여부와 종료 사유: 3아웃, 끝내기 등.
- 화면용 송구·포구·태그 시각. 규칙상 순서와 일치시킨다.

위 항목의 명칭은 구현 시 한국어 설명과 기존 코드 관례에 맞춰 정한다. `runs`처럼 이동 목록에서 유도되는 값은 한 곳에서 계산하고 일치 여부를 검증한다. 규칙과 화면에서 각각 난수로 진루를 다시 뽑지 않는다.

기존 `applyEvent(state, type)` 호출은 볼·스트라이크·파울부터 호환을 유지하고, 인플레이 결과를 단계적으로 새 형식에 연결할 수 있다. 직접 경기·자동 진행·이닝 넘기기·시즌 시뮬레이션이 같은 판정 경로를 사용해야 한다. 새 형식 도입은 기존 커리어 저장 형식 전체 변경과 분리한다.

## 5. 권장 구현 순서와 완료 조건

### 1단계: 명확한 오류와 화면 모순 제거

- R1 끝내기 초과 득점과 파생 기록 수정.
- V1 송구 도착·포구 시각 통합.
- V2 현재 판정에 맞는 주자 귀루 누락 보완.
- S1 와일드카드 무승부 진출 조건은 별도 변경으로 처리 가능.

완료 조건: 알려진 재현 사례가 해결되고 기존 경기 종료·볼넷·파울 규칙이 유지된다. 이 단계에서는 상황별 주루 전체를 바꾸지 않는다.

### 2단계: 주루 결정 통합과 상황 반영

- 공통 주자 이동·아웃 결과 도입.
- R2 태그업 시도와 희생플라이 기록 분리.
- R3 짧고 깊은 안타에 따른 진루 구분.
- V4 아웃 수에 따른 출발·귀루 반영.
- 세 번째 아웃의 종류와 득점 순서를 함께 처리.

완료 조건: 규칙의 최종 베이스 상태와 재생 후 주자 위치가 일치하고, 주자 중복·누락과 잘못된 득점이 없다.

### 3단계: 수비 선택과 동작 개선

- D1 야수선택·홈 승부·투수/포수 타구 처리 추가.
- V3 속도 제한과 결과를 만족하는 장면 생성·검증.
- 화면 문구·경기 로그·성장·선수 기록까지 새 결과 연결.

완료 조건: 세이프·아웃이 실제 재생된 포구·베이스 접촉·태그 순서와 일치한다. 시뮬레이션의 타율·홈런·볼넷·삼진 분포도 기존 밸런스 검사 범위를 확인한다.

### 후속 검토

홈/원정, 실제 포스트시즌 연장 제한, 선수별 주력·수비·송구 능력, 라인업 수비 포지션 반영은 후속 개선으로 둔다. 도루·견제·실책·사구·폭투·패스트볼·번트·낫아웃·인필드 플라이 등은 별도 규칙 설계가 필요하다. 현재 없는 기능을 모두 첫 수정에 넣을 필요는 없다.

## 7. 이전 검토 내용의 정정

- “끝내기를 유지한다”는 이전 방침을 정정한다. 종료 판단 자체는 있으나 초과 득점 오류가 확인되어 수정이 필요하다.
- “땅볼이면 주자가 반드시 한 베이스씩 진루한다”, “무사 만루 병살이면 항상 득점한다”는 설명은 정확하지 않다. 아웃 순서와 포스 해제, 실제 주루에 따라 달라진다.
- “홈 송구는 항상 주자보다 늦다”는 설명을 정정한다. 실제로 늦추는 것은 포수의 포구 시각이며 송구 구간은 더 일찍 끝날 수 있다.
- 기존 문서의 단타 송구 관련 “300개 중 64개(21%), 뜬공 약 8%”는 이번 재검증 조건에서 재현되지 않았다. 확인된 발생률로 사용하지 않으며, 원래 입력과 측정 방법을 복원하기 전에는 결론의 근거로 삼지 않는다.
- 병살 확률 35%를 실제보다 높다고 단정하거나 15%를 정답으로 제시하지 않는다. 비교 통계와 게임 밸런스를 보고 정할 조정값이다.
- `fly`만으로 단타 진루를 고정하거나 모든 2루타에서 전원 득점시키는 방안은 확정안으로 채택하지 않는다. 또 다른 고정 진루가 되어 같은 현실성 문제가 남는다.
